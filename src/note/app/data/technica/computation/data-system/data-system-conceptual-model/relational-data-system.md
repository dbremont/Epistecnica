# Relational Data System

- [Relational Data Model](note.html?n=technica/computation/data-system/data-system-conceptual-model/relational-data-model.md)

> A **Relational Data System (RDS)** is a type of database system that organizes and manages data using the **relational model**, where information is represented in **tables (relations)** consisting of **rows (tuples)** and **columns (attributes)**.
> 

## Data Model

> The **relational data model** is a conceptual framework that defines mechanisms to **represent data**, specify **operations** on that data, and provide a **formal semantics** that gives a precise meaning to the representations and operations.
> 

> See more in [Relational Data Model](note.html?n=technica/computation/data-system/data-system-conceptual-model/relational-data-model.md).
> 

## Query Language

> A **query language** is a formal language used to request, filter, and manipulate data stored in a database or information system. Unlike general-purpose programming languages, query languages are typically **declarative**: they let users specify *what* data they want rather than *how* to retrieve it, leaving the execution strategy to the database engine.
> 

> See more in [Query Language](note.html?n=technica/computation/data-system/data-system-conceptual-model/query-language.md).
> 

## Architecture

> Database engine architecture refers to the underlying structure and design decisions made to store, manage, and access data efficiently and reliably, often involving components such as storage, query processing, concurrency control, security, and performance optimization.
> 

| Architecture Type | Description |
| --- | --- |
| **Disk-based Architecture** | Data is stored on disk and accessed via disk I/O operations. This architecture is typical for relational databases where data is organized into tables on disk and accessed through SQL queries. It's favored for its durability and ability to manage large volumes of data. |
| **In-memory Architecture** | Data is stored directly in memory, allowing for much faster access than disk I/O. This architecture is suitable for applications requiring high-speed data processing, such as real-time analytics and trading systems. |
| **Distributed Architecture** | Data is stored across multiple nodes in a distributed system, enhancing scalability and fault tolerance. Techniques such as sharding and replication are used to distribute data across nodes, ensuring high availability and performance at scale. |
| **Hybrid Architecture** | Combines multiple database architectures within a single system, such as disk-based architecture for storing historical data and in-memory architecture for processing real-time data. This approach allows for flexibility in data handling and optimization for different data access patterns. |

| **Storage Management** | **Buffer Manager** | Manages memory buffers for temporary data storage, optimizing disk I/O operations. |
|  | **Storage Engine** | Handles physical storage, organization, and retrieval of data on disk. |

| **Transaction Management** | **Transaction Manager** | Manages transactions to ensure data integrity and consistency and controls locking and concurrency. |
|  | **Lock Manager** | Manages locks to allow multiple transactions to access the same data safely, preventing conflicts by granting and releasing locks according to predefined modes. |
| **Metadata Management** | **Schema Manager** | Manages database schemas and metadata, including creation and modification of tables and indexes. |

|  | **Recovery Manager** | Ensures database consistency and durability after failures. Logs changes, rolls back or redoes transactions, and restores a consistent state after crashes. |

## Representation

> What are the **database subjects (object) (tables, index, …)** to be represented? Which are the representation models? Which are the representational mechanisms?
> 

### Data Model Representation

> Which inner structured to we need to represented?
> 

| **Inner Structure** | **Description** |
| --- | --- |
| **Table (Relation)** | Primary data container, stores rows (tuples) and columns (attributes). Represented on disk as **pages/blocks**, in memory as **row-oriented arrays**, **columnar blocks**, or **hash tables**. Supports CRUD operations, indexing, and query evaluation. |
| **Index** | Auxiliary structure to accelerate data access. Implemented as **B-trees, hash indexes, or bitmap indexes**. May exist on disk and in memory for fast lookups, joins, and range queries. |
| **View** | Virtual table representing a stored query. Can be **materialized** (physically stored) or **non-materialized** (computed on demand). Facilitates abstraction and query simplification. |
| **Constraint** | Rules enforcing **data integrity**, such as primary keys, foreign keys, unique constraints, and check constraints. Ensures consistency and correctness of data. |
| **Schema (Metadata)** | Describes the structure of tables, columns, data types, relationships, and constraints. Stored in **system catalogs** and used by the DBMS for query planning and validation. |
| **Sequence (Counter)** | Mechanism to generate unique identifiers, often used for primary keys. Can be persistent (stored on disk) or cached in memory for efficiency. |
| **Temporary Table (Intermediate Structure)** | Used during query execution for joins, sorting, grouping, or aggregation. Usually resides **in memory** but may spill to disk if too large. |
| **Buffer (Cache)** | In-memory copy of disk pages or frequently accessed data. Improves read/write performance and reduces I/O latency. |
| **Transaction Log** | Records all modifications for durability and recovery. Stored on disk but may be buffered in memory for performance. |
| **Lock (Latch Table)** | Tracks locks and latches for concurrency control. Usually maintained **in memory** to coordinate multi-user access. |

### Mechanism

> How to represent  the `representation mechanisms`?
> 

> A **mechanism** is a concrete method or structure by which a Relational Data System **implements, organizes, stores, or manipulates data**. Mechanisms are the operational components that realize the conceptual representation defined by the models. They determine how data is physically managed in memory and on storage media, and how queries are executed efficiently.
> 

| **Category** | **Mechanism** | **Description** |
| --- | --- | --- |
| **In-Memory Data Representation** | Row-oriented Array | Store each row contiguously in RAM; efficient for transactional workloads (OLTP). |
|  | Columnar Block | Store each column contiguously in RAM; optimized for analytical workloads (OLAP). |
|  | Hash Table (Dictionarie) | Enable fast key-based lookups and joins in memory. |
|  | Caching Mechanism | Buffer pools, page caches, and query result caches to reduce disk I/O and improve performance. |
| **Out-of-Memory (Persistent) Data Representation** | Page (Block) | Disk or SSD units used to read/write data efficiently. |
|  | Storage Format | Row-store, column-store, or hybrid layouts optimized for specific workloads. |
|  | Log Structure | Transaction logs (Write-Ahead Logs) to ensure durability and support recovery. |
| **Query Execution Structures** | Intermediate Result Table | Temporary tables storing results of subqueries, joins, and aggregations. |
|  | Hash Table (Join Buffer) | Support efficient join and grouping operations during query execution. |
|  | Sort Buffer (Priority Queue) | Used for ORDER BY, TOP-N queries, and window functions. |
| **Concurrency & Transaction Mechanisms** | Lock Table (Latche) | Track resource locks in memory to maintain consistency during concurrent access. |
|  | MVCC (Multi-Version Concurrency Control) | Maintains multiple versions of data to allow concurrent reads and writes without blocking. |
| **Persistence & Recovery Mechanisms** | Write-Ahead Logs (WAL) | Sequentially log changes before applying them to disk to ensure durability. |
|  | Checkpoint (Snapshot) | Periodic persistent states of the database to accelerate recovery after failures. |

## **Cross-functional Subsystem**

> Which  the cross functionality in  a Relational Database System?
> 

> Components that provide functionality spanning multiple areas of the database, enhancing performance, reliability, and security.
> 
- **Indexing** – Provides fast access to data across tables, benefiting queries, updates, and joins.
- **Transactions & Concurrency Control** – Ensures consistency and isolation when multiple operations occur simultaneously.
- **Caching / Buffer Management** – Optimizes disk I/O by keeping frequently accessed data in memory.
- **Query Statistics / Cost Estimation** – Helps the query optimizer choose the most efficient execution plan.
- **Security & Access Control** – Enforces user privileges and protects data integrity across all operations.
- **Logging & Recovery / Crash Recovery** – Maintains write-ahead logs (WAL) to recover from failures.
- **Replication / High Availability Subsystems** – Ensures data redundancy and fault tolerance across nodes.
- **Monitoring & Performance Metrics** – Tracks query performance, resource usage, and system health.
- **Data Partitioning & Sharding** – Splits data across multiple storage locations to improve scalability and parallelism.
- **Foreign Key & Integrity Enforcement** – Ensures relational constraints are maintained across multiple tables.
- **Materialized Views / Result Caching** – Precomputes and stores query results to improve response times.
- **Compression & Storage Optimization** – Reduces storage footprint and improves I/O efficiency.
- **Audit Trails / Compliance Subsystems** – Tracks user actions for compliance and accountability.

### Performance Trick

| Optimization Trick | Description |
| --- | --- |
| **Indexing** | Use indexes on columns that are frequently used in queries to speed up data retrieval. |
| **Query Caching** | Store the results of commonly or recently executed queries to reduce the need to execute them again. |
| **Partitioning** | Divide a database into partitions to spread data across multiple machines or disks. |
| **Data Compression** | Compress data to reduce storage requirements and improve I/O efficiency. |
| **Denormalization** | Reduce the number of joins needed for queries by including redundant data across tables. |
| **Query Rewriting** | Rewrite queries to optimize their execution plans, such as by avoiding sub-optimal joins. |
| **Parallel Processing** | Utilize multiple processors or cores to handle different parts of a query or different queries. |
| **Load Balancing** | Distribute workloads evenly across servers to avoid overloading any single system. |
| **Materialized Views** | Store the results of a complex query physically; useful for frequently accessed, computation-intensive queries. |
| **Connection Pooling** | Use a pool of database connections to reduce the overhead of opening and closing connections. |
| **Parallelization** |  Utilize parallel processing techniques, such as partitioning and pipelining, to distribute query processing across multiple processors and reduce query response time. |
| **Storage Format** | Based on the application's specific needs, choose an appropriate format for storing data, such as row-based, column-based, or hybrid storage. |
